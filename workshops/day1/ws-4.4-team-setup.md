## 👉 ขั้นตอน

### ขั้นที่ 1 — ตกลงบทบาท 4 บทบาท

| บทบาท | หน้าที่ | ใช้ในวันที่ 2 |
|---|---|---|
| **Module Lead** | ดูภาพรวมโมดูล, ตัดสินเรื่องลำดับงาน, ประสานกับทีมอื่น | ตัดสินเมื่อ conflict ข้ามโมดูล |
| **Spec Approver** | อนุมัติ Spec ด้วยมือ | **ประตูมนุษย์ที่ 1** (WS6.2) |
| **PR Reviewer** | ตรวจ PR ข้ามทีม | **ประตูมนุษย์ที่ 2** (WS7.3) |
| **Memory Scribe** | บันทึกบทเรียนลง Memory hub ผ่าน PR | WS7.3, WS8.3 |

(ทีมที่มีสมาชิก 4–6 คน: 1 คนถือได้มากกว่า 1 บทบาท และสลับกันได้)

### ขั้นที่ 2 — เขียน `TEAM.md`

สร้างกิ่ง `docs/team-setup` แล้วสร้างไฟล์ **`TEAM.md`**:

```markdown
# ทีม <N> — โมดูล <ชื่อโมดูล>

| บทบาท | ชื่อ | GitHub |
|---|---|---|
| Module Lead | | @ |
| Spec Approver | | @ |
| PR Reviewer | | @ |
| Memory Scribe | | @ |

สมาชิกอื่น: ...

ช่องทางสื่อสารของทีม: ...
```

### ขั้นที่ 3 — เขียน Working Agreement 5 ข้อ ลง `CONTRIBUTING.md`

ตัวอย่าง (ให้ทีมปรับเอง):

```markdown
## Working Agreement ของทีม <N>

1. ไม่ commit ตรงเข้า main — ทุกงานผ่าน Pull Request
2. ทุก PR ผูก Issue (`Closes #เลข`) และมีผู้ตรวจอย่างน้อย 1 คน
3. ตอบ Review ภายใน 30 นาทีในวัน Sprint
4. ติดเกิน 10 นาที ถามทีมก่อน แล้วค่อยเรียก TA
5. ข้อความ commit ใช้รูปแบบ `type(scope): สรุป (#เลข)`
```

### ขั้นที่ 4 — Commit, Push และเปิด PR

```bash
git add TEAM.md CONTRIBUTING.md
git commit -m "docs: add team roles and working agreement"
git push -u origin docs/team-setup
gh pr create --base main --fill
```

ให้ทีม Review → Merge

### ขั้นที่ 5 — สร้างการ์ดของโมดูลใน **`dms-central`**

> ⚠️ ใน **`dms-central`** (repo กลาง ไม่ใช่ repo ฝึกหัด) — ผู้สอนตั้ง Board และ Template ไว้แล้ว

ทีมช่วยกันเปิด Issue **อย่างน้อย 5 ใบ** สำหรับโมดูลของทีม:

- ใช้แม่แบบ **Feature**
- เขียน **User story + AC ที่ตรวจได้** (ตรวจกันเองข้ามคน)
- ติด `module: <โมดูลของทีม>` และ `type: feature`
- ขนาดเล็กพอทำจบใน **1 Session** (ประมาณ 1 ชั่วโมงรวม Spec + โค้ด)
- ตัวอย่างลำดับ: endpoint พื้นฐาน → กรณีขอบ → ตรวจสิทธิ์ → หน้าจอ

### ขั้นที่ 6 — แจ้ง GitHub username ให้ผู้สอน

เขียน username ของทุกคนในทีมตามบทบาท ส่งให้ผู้สอน (เพื่อผูกกับ Team ใน Organization และ `CODEOWNERS`)

## ✅ Checkpoint (ตรวจตัวเอง)

- [ ] `TEAM.md` และ `CONTRIBUTING.md` merge เข้า `main` ของ repo ฝึกหัดแล้ว
- [ ] มีการ์ด `module: <โมดูลของทีม>` ใน `dms-central` อย่างน้อย 5 ใบ และ AC ตรวจได้
- [ ] ทุกคนรู้บทบาทของตัวเอง

## 🔧 ปัญหาที่พบบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| เปิด Issue ใน `dms-central` ไม่ได้ | ยังไม่ได้อยู่ใน Team `participants` | แจ้งผู้สอน |
| การ์ดใหญ่เกินไป | ไม่แตก AC | แตกเป็นหลายใบ ให้แต่ละใบมี AC ไม่เกิน 3–4 ข้อ |
| ทีมเถียงกันเรื่องบทบาท | — | ตัดสินว่าบทบาทไหนใครถือ **วันนี้** แล้วสลับได้พรุ่งนี้ |

## 🧪 ท้าทายเพิ่ม

- เขียนการ์ด "Spike" (งานสำรวจ) 1 ใบ: คำถามที่ทีมยังไม่รู้เกี่ยวกับโมดูลของตัวเอง
- เขียน "Definition of Done" 3 ข้อของทีมลง `CONTRIBUTING.md`

## 🧑‍🏫 หมายเหตุสำหรับผู้สอน/TA

- ทีมถูกจัดจากแบบสำรวจความคุ้นเคยเพื่อให้ทักษะสมดุล — ประกาศโมดูลก่อนเริ่มงานนี้
- ตรวจคุณภาพการ์ดแบบสุ่ม: การ์ดที่ดี = AC ตรวจได้ + เล็กพอ — วันพรุ่งนี้ทีมจะ "ได้สิ่งที่เขียน" เสมอ (AI จะอ่านการ์ดเหล่านี้)
- เก็บ GitHub username → ผูก Team `team-1`…`team-5` → ใช้ใน `CODEOWNERS` ของ `dms-central`
- ปิดวันด้วยการทบทวน: Issue Template · Label · Board · CI · Ruleset · Release `v0.0.1` — แล้วเกริ่นว่าพรุ่งนี้ AI จะเข้ามาทำงานภายใต้ฐานนี้
