## 🎯 เป้าหมาย

รวมงานของหลายทีมเข้า `main` **ทีละทีม ตามลำดับ** โดยไม่ทำให้ของเพื่อนพัง — ใช้ทักษะ PR, Review, Conflict และ CI ที่เรียนมาทั้งสองวัน

## 💡 หลักการ: ทีละทีม — pull → test → merge

1. **ทีละทีม** ตามคิว (ไม่ merge พร้อมกัน)
2. ก่อน merge ทุกครั้ง: `git pull` main ล่าสุดเข้ากิ่งตัวเอง → `npm run migrate && npm test` → ถึงค่อย merge
3. หลัง merge: ทีมที่เหลือ **ดึง main ใหม่** แล้วรันใหม่ เพราะ main เปลี่ยนแล้ว

**จุดที่มักชนกัน:** `openapi.yaml` (สัญญากลาง), ไฟล์รวม routes, **ลำดับไฟล์ migration**, `package.json`

## 📋 ต้องมีก่อนเริ่ม

- PR ของทีมผ่าน CI และมี Review จากคนต่างทีม (WS7.3)
- ผู้สอนประกาศลำดับ merge: **ทีม 1 → 2 → 3 → 4 → 5** (หรือตามที่ตกลง)

## 👉 ขั้นตอน (สำหรับทีมที่ถึงคิว)

### ขั้นที่ 1 — อัปเดตกิ่งด้วย `main` ล่าสุด

```bash
git switch <กิ่งของ PR ที่จะ merge>
git fetch origin
git merge origin/main
```

### ขั้นที่ 2 — ถ้ามี conflict แก้ร่วมกับทีมก่อนหน้า

ใช้วิธีเดียวกับ [WS2.2](../day1/ws-2.2-merge-conflict.md): เปิดไฟล์ใน VS Code ตัดสินใจร่วมกัน (โดยเฉพาะ `openapi.yaml` — ต้อง **เก็บ endpoint ของทั้งสองทีม**)

**กรณี migration:** ถ้าสองทีมเพิ่มไฟล์ migration ที่ลำดับ/ชื่อชนกัน ให้เปลี่ยนตัวเลขลำดับของทีมที่มาทีหลัง และตรวจว่า migration รันตามลำดับได้ (`npm run migrate` บนฐานข้อมูลสะอาด)

```bash
git add -A
git commit -m "chore: merge main into <กิ่ง>"
```

### ขั้นที่ 3 — รันทุกอย่างใหม่

```bash
docker compose down -v      # ล้างฐานข้อมูลเดิม (ข้อมูลทดลองหายทั้งหมด)
docker compose up -d
npm ci
npm run migrate
npm run seed
npm test
```

✅ **ต้องเห็น:** `npm test` ผ่านทั้งหมด (รวม Test ของทีมก่อนหน้า)

### ขั้นที่ 4 — Push, รอ CI, ขอ Approve แล้ว Merge

```bash
git push
```

ตรวจ PR: CI เขียว · Approve จากคนต่างทีม (และ Code Owner) → **Squash and merge** → ลบกิ่ง

### ขั้นที่ 5 — แจ้งทีมถัดไป

ประกาศบนจอ/กลุ่ม: "ทีม <N> merge แล้ว ทีมถัดไปดึง `main` ได้"

### ขั้นที่ 6 — ทดสอบเส้นทางข้ามโมดูล (หลัง merge ครบหรือหลังแต่ละทีม)

เมื่อทุกทีม merge แล้ว ทำ **Integration test** บนเครื่องใดเครื่องหนึ่ง (ผู้สอนฉายจอ):

1. **อัปโหลด** เอกสารใหม่ (ทีม 1)
2. **ค้นหา** เอกสารนั้นด้วยแท็ก (ทีม 2)
3. ดู **เวอร์ชัน** และสร้างเวอร์ชันใหม่ (ทีม 3)
4. **ส่งอนุมัติ → อนุมัติ** (ทีม 4)
5. ตรวจ **สิทธิ์**: ผู้ใช้ที่ไม่มีสิทธิ์ถูกปฏิเสธ (ทีม 5)

✅ **ต้องเห็น:** ทุกขั้นทำงานต่อเนื่อง ถ้าขั้นใดพังเปิด Issue `type: bug` + `module: …` แล้วให้ทีมเจ้าของโมดูลแก้ผ่าน PR

## ✅ Checkpoint (ตรวจตัวเอง)

- [ ] PR ของทีมคุณ merge เข้า `main` แล้ว (หรืออยู่ในคิว)
- [ ] CI บน `main` เขียวหลัง merge
- [ ] `npm test` ผ่านเมื่อรวมงานของทุกทีมที่ merge แล้ว
- [ ] เส้นทางข้ามโมดูลใช้งานได้ หรือมี Issue บันทึกจุดที่พัง

## 🔧 ปัญหาที่พบบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| conflict ใน `openapi.yaml` | สองทีมเพิ่ม endpoint ใกล้กัน | เก็บของทั้งสองทีม ตรวจไวยากรณ์ YAML ให้ถูก |
| `migrate` ล้มหลัง merge | ลำดับ migration ชนกัน | เปลี่ยนลำดับของทีมที่มาทีหลัง ทดสอบบน DB สะอาด |
| CI แดงบน `main` | ปัญหาข้ามโมดูล | เปิด Issue `type: bug` แล้วแก้ผ่าน PR ด่วนที่มี Review |
| Test ของทีมอื่นพังเพราะของเรา | เปลี่ยน contract/ข้อมูล seed | คุยกับทีมนั้น ปรับให้เข้ากัน (Discussions → decisions.md) |

## 🧪 ท้าทายเพิ่ม

- เขียน integration test เส้นทางเดียวข้ามโมดูลเก็บไว้ใน repo
- บันทึกลง `docs/memory/lessons.md` ว่าการรวมโมดูลครั้งนี้มีอะไรที่ควรทำต่างไป (ผ่าน PR)

## 🧑‍🏫 หมายเหตุสำหรับผู้สอน/TA

- ผู้สอนถือคิวและควบคุมจังหวะ merge บนจอหลัก (ใช้ Board ติดตาม: In Review → Done)
- ถ้ามีทีมที่ PR ยังไม่พร้อม ให้ข้ามไปทีมถัดไป แล้วกลับมาท้ายคิว — อย่าบล็อกทั้งห้อง
- เป็นโอกาสสอนจริงเรื่อง **สัญญากลาง (API contract)**: การเปลี่ยน `openapi.yaml` ควรผ่าน Discussion/Maintainer
- เวลา 15′ ตึง: ถ้าทีมใหญ่เกิน ให้ merge เฉพาะ PR หลักของแต่ละทีมก่อน (ที่เหลือหลังอบรม) และเก็บการ์ดที่เหลือเป็น Backlog ของรอบหน้า
