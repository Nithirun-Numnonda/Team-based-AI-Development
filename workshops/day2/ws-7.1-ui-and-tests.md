## 🎯 เป้าหมาย

ใช้ Flow 3 บทบาท **ซ้ำอีกรอบ** กับงานหน้าจอ (UI) และ Test โดยฝึกวินัยเดิม: **Spec ก่อน → คนอนุมัติ → Builder → อ่าน diff**

## 📋 ต้องมีก่อนเริ่ม

- ผ่าน [WS6.3](ws-6.3-builder-api-pr.md) แล้ว (API ของการ์ดทำงาน) หรือหยิบการ์ดใหม่ที่ทำ Spec + อนุมัติแล้ว
- Docker/DB ยังรันอยู่ (`docker compose ps`) และ `npm test` เขียว

> หมายเหตุ: รูปแบบของ "หน้าจอ" ขึ้นกับ Starter ที่ผู้สอนเตรียม (เช่น หน้า HTML ที่ API เสิร์ฟ หรือ front-end ง่าย ๆ) — ผู้สอนจะบอกโฟลเดอร์ที่ใช้ก่อนเริ่ม

## 👉 ขั้นตอน

### ขั้นที่ 1 — ให้ Designer เพิ่มส่วน UI ลง Spec

**Kilo Code → New Task → Agent `designer`** แล้ว prompt:

```text
ทำหน้าที่ Designer สำหรับ Issue #<N> (Spec อยู่ที่ docs/specs/<N>-*.md และ Handoff ที่ docs/handoff/<N>.md)
เพิ่ม "ส่วน UI" ลงใน Spec: หน้าจอ/ฟอร์ม/ตารางที่ต้องมีสำหรับ Acceptance Criteria ของการ์ดนี้
ระบุ: ชื่อหน้า องค์ประกอบ (ช่องกรอก ปุ่ม ตาราง) พฤติกรรมเมื่อมีข้อผิดพลาด และกรณีทดสอบที่เกี่ยวกับหน้าจอ
อ่าน AGENTS.md และ docs/memory ก่อน ห้ามแก้ไฟล์ใน src/
```

### ขั้นที่ 2 — ประตูมนุษย์ที่ 1 อีกรอบ (สั้น ๆ)

อ่านเฉพาะ **ส่วนที่เพิ่ม** ด้วย 5 คำถามเดิม (ดู [WS6.2](ws-6.2-human-gate-1.md)) → ติ๊ก Handoff อีกครั้งด้วยมือ → commit:

```bash
git add docs/specs docs/handoff
git commit -m "docs(spec): add UI section for #<N>"
```

### ขั้นที่ 3 — Builder สร้างหน้าจอ

**Cline → New Task → Plan →** `/build.md` → ตอบ `<N>`

1. อ่านแผน: ต้องอ้าง Spec **ส่วน UI** และไฟล์ที่ระบุ
2. สลับ **Act** → **อ่าน diff ทุกไฟล์** ก่อน Save
3. เปิดหน้าจอบนเครื่อง (`npm run dev` → เปิดที่ `http://localhost:3000/...`) ตรวจเองตาม AC

### ขั้นที่ 4 — ให้ Builder เพิ่ม Test

พิมพ์ใน Cline:

```text
เพิ่ม Unit/API Test ของการ์ด #<N> ให้ครอบคลุมกรณีทดสอบทั้งหมดใน Spec (ปกติ กรณีขอบ ผิดพลาด) ห้ามลบหรือลด Test เดิม
```

อ่าน diff → Save → รัน `npm test`

✅ **ต้องเห็น:** Test ใหม่ผ่านทั้งหมด และจำนวน Test เพิ่มขึ้น

### ขั้นที่ 5 — เขียน Test เพิ่มด้วยมือ 1 ข้อ

คิดกรณีขอบที่ AI ลืม (เช่น ค่าว่าง, ตัวอักษรไทย, ข้อมูลจำนวนมาก, สิทธิ์ผิดบทบาท) แล้ว **เขียน Test เองอย่างน้อย 1 ข้อ** (ขอ AI อธิบายโครงสร้าง test ได้ แต่คุณพิมพ์เอง) → `npm test`

### ขั้นที่ 6 — Commit ทีละงาน และอัปเดต Handoff

```bash
git add <ไฟล์หน้าจอ>
git commit -m "feat(<โมดูล>): add <ชื่อหน้า> UI (#<N>)"
git add <ไฟล์ test>
git commit -m "test(<โมดูล>): cover <กรณี> (#<N>)"
```

ตรวจว่า **Handoff ส่วน 2) Build** อัปเดตแล้ว (ไฟล์ที่เปลี่ยน, ผลทดสอบ, สิ่งที่เบี่ยงจาก Spec)

## ✅ Checkpoint (ตรวจตัวเอง)

- [ ] ส่วน UI ใน Spec ได้รับอนุมัติด้วยมือคุณก่อนที่ Builder จะเริ่ม
- [ ] หน้าจอทำงานตาม AC ที่คุณตรวจเอง
- [ ] `npm test` ผ่าน และมี Test ที่ **คุณเขียนเอง** อย่างน้อย 1 ข้อ
- [ ] commit แยกตามงาน และ Handoff ส่วน 2 อัปเดต
- [ ] Auto-approve ยังปิดอยู่

## 🔧 ปัญหาที่พบบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| Builder ลบ/ลด Test เพื่อให้ผ่าน | AI "แก้ให้ผ่าน" แทนแก้โค้ด | **Reject ทันที** แล้วพิมพ์ "ห้ามแก้ Test เดิม ให้แก้โค้ดให้ผ่าน" |
| หน้าจอไม่ตรง Spec | Spec ส่วน UI ไม่ละเอียด | กลับไปให้ Designer เติม แล้วอนุมัติใหม่ ก่อน Build |
| Test ผ่านแต่ใช้งานจริงพัง | Test ไม่ครอบคลุม | เพิ่ม Test จากการทดลองด้วยมือ |
| UI ขึ้นแต่ข้อมูลว่าง | ยังไม่ `seed` หรือ token ผิดบทบาท | `npm run seed` · ตรวจ token ตามสิทธิ์ |

## 🧪 ท้าทายเพิ่ม

- ให้ Reviewer (Kilo) ตรวจ Test ของคุณว่า "มีกรณีไหนที่ Test ผ่านแต่โค้ดผิดได้" (ใช้ใน WS7.2 ต่อ)
- เพิ่มกรณีข้อมูลภาษาไทยในชื่อเอกสาร/แท็ก แล้วดูว่าการค้นหา/แสดงผลถูกต้อง

## 🧑‍🏫 หมายเหตุสำหรับผู้สอน/TA

- ตรวจว่าผู้เรียน **ไม่ข้ามประตูที่ 1** เพราะ "แค่ทำ UI" — ย้ำว่าส่วนที่เพิ่มต้องผ่านการอนุมัติเหมือนเดิม
- ผู้เรียนที่เก่งแล้วให้ท้าทาย: เขียน Test ที่ "จับ" บั๊กที่ AI อาจสร้าง
- ระวังคนเปิด Auto-approve เพราะรู้สึกว่ามั่นใจแล้ว — เตือนซ้ำว่ากติกาคือ "อ่านก่อนกด" ตลอดงาน
- ยืนยันก่อนวันอบรมว่า Starter มีโครงหน้าจอพร้อมใช้ (เช่น โฟลเดอร์หน้า HTML/view) ไม่เช่นนั้นกำหนดรูปแบบหน้าจออย่างง่ายให้ทุกทีม
