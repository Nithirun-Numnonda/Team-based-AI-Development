## 🎯 เป้าหมาย

ผ่าน **ประตูมนุษย์ที่ 2**: คนที่รับผิดชอบโค้ด อ่าน ถาม และตัดสิน — แล้วเปลี่ยนสิ่งที่ได้เรียนรู้ให้เป็น **ความจำของทีม** ผ่าน PR

## 📋 ต้องมีก่อนเริ่ม

- PR ของคุณเปิดแล้ว มี CI + Comment ของ Bot (จาก [WS7.2](ws-7.2-reviewer-and-bot.md))
- ผู้สอนจับคู่ข้ามทีมให้ (หรือจับคู่เองคนละทีม)

## 👉 ขั้นตอน (ส่วน A — ประตูมนุษย์ที่ 2)

### ขั้นที่ 1 — เปิด PR ของคู่

เปิดลิงก์ PR ของเพื่อนต่างทีม → แท็บ **Files changed**

### ขั้นที่ 2 — ตรวจ 4 สัญญาณของ Flow ที่ถูกต้อง

| # | สัญญาณ | ดูที่ | ผ่าน? |
|---|---|---|---|
| (ก) | มีไฟล์ **Spec** ใน PR | แท็บ Files changed | ☐ |
| (ข) | Handoff ส่วน 1 **ติ๊กโดยคน** (ไม่ใช่ AI) | `docs/handoff/<N>.md` | ☐ |
| (ค) | Handoff ส่วน 3 มี **ผลตรวจ** ของ Reviewer | `docs/handoff/<N>.md` | ☐ |
| (ง) | มี **Comment ของ Bot** | แท็บ Conversation | ☐ |

และดูแท็บ **Commits**: commit แรกควรเป็น `docs(spec): …`

### ขั้นที่ 3 — อ่านโค้ดตาม Checklist และ **ถามอย่างน้อย 1 คำถาม**

อ่านไฟล์จริงทุกไฟล์ (ไม่ใช่แค่ Comment ของ Bot) ตาม Checklist:

- [ ] ตรงกับ Issue / Spec ครบ Acceptance Criteria
- [ ] มี Test และกรณีขอบ
- [ ] อ่านง่าย ชื่อสื่อความหมาย
- [ ] ปลอดภัย: ไม่มี secret, ตรวจ input และสิทธิ์
- [ ] แตะเฉพาะไฟล์ที่ควรแตะ
- [ ] เจ้าของ PR อธิบายโค้ดได้

วางเมาส์ที่บรรทัดแล้วกด **+** เพื่อถาม — **ต้องถามอย่างน้อย 1 ข้อ** เช่น

```text
ที่เลือกคืน 404 แทน 200 พร้อมรายการว่างเพราะอะไร ใน Spec ระบุไว้ตรงไหน?
```

💡 **ทำไมต้องถาม:** การ Approve โดยไม่ถามอะไรเลย มักแปลว่าไม่ได้อ่านจริง — คำถามเดียวก็พอให้รู้ว่าเจ้าของ PR เข้าใจโค้ดที่ AI เขียนให้หรือไม่

### ขั้นที่ 4 — ตัดสินใจ

กด **Review changes** → เลือก

- **Approve** (พร้อมสรุปสั้น ๆ) ถ้าพอใจ
- **Request changes** ถ้ายังมีปัญหา (บอกเหตุผลและทางแก้)

→ **Submit review**

### ขั้นที่ 5 — เจ้าของ PR กรอก Handoff ส่วนที่ 4

กลับไปกรอก **ส่วน 4) Human decision** ใน `docs/handoff/<N>.md` รวมหัวข้อ **"ข้อที่ AI Review พลาด/แจ้งเกินจริง"** (ใช้ตารางจาก WS7.2) → Commit → Push

## 👉 ขั้นตอน (ส่วน B — บทเรียนเข้า Memory hub)

> ทำโดย **Memory Scribe** ของแต่ละทีม (คนอื่นช่วยเสนอบทเรียน)

### ขั้นที่ 6 — คัดบทเรียน 1 ข้อ

ข้อที่ดี = **สั้น ตรวจได้ ชี้ PR ต้นทาง** และใช้ป้องกันความผิดพลาดซ้ำได้ เช่น

```markdown
- [2026-10-28] AI ลืมคืนค่า 0 ให้สถานะที่ไม่มีเอกสาร → ระบุกรณี "ไม่มีข้อมูล" ใน Spec ทุกครั้งที่มีการนับ (PR #…)
- [2026-10-28] Bot แจ้งเตือนเรื่องสไตล์ที่ทีมไม่ได้กำหนด → เพิ่มข้อตกลงใน conventions.md ก่อนค่อยบังคับ (PR #…)
```

### ขั้นที่ 7 — เปิด PR เพิ่มบทเรียน

```bash
git switch main && git pull
git switch -c docs/memory-lesson-<เรื่องสั้น>
```

เปิด `docs/memory/lessons.md` เพิ่ม **1 บรรทัดท้ายไฟล์** → Commit → Push → เปิด PR:

```bash
git add docs/memory/lessons.md
git commit -m "docs(memory): add lesson about <เรื่อง> (#<N>)"
git push -u origin docs/memory-lesson-<เรื่องสั้น>
gh pr create --base main --fill
```

### ขั้นที่ 8 — Maintainer ตรวจและ Merge

ไฟล์ใน `docs/memory/` ต้องให้ **Maintainer (Code Owner)** Approve — แจ้ง Maintainer ว่ามี PR รอ เมื่อ merge แล้ว AI ทุกตัวที่อ่าน Memory hub จะ "จำ" บทเรียนนี้ได้ในงานถัดไป (ทดสอบใน [WS8.3](ws-8.3-sprint-review-memory.md))

## ✅ Checkpoint (ตรวจตัวเอง)

- [ ] PR ของคุณมี Review จากคนต่างทีมอย่างน้อย 1 คน และมีคำถามอย่างน้อย 1 ข้อ
- [ ] คุณตรวจ 4 สัญญาณของ Flow ของ PR เพื่อนได้ครบ
- [ ] Handoff ส่วน 4 กรอกแล้ว
- [ ] มี PR บทเรียนของทีมที่ Maintainer ตรวจ (merge หรือรอ merge ใน WS8.3)

## 🔧 ปัญหาที่พบบ่อย

| อาการ | สาเหตุ | วิธีแก้ |
|---|---|---|
| "Waiting on code owner review" | ผู้ Approve ไม่ใช่ Code Owner ของไฟล์นั้น | ให้ Code Owner (เจ้าของโมดูล/Maintainer) Approve |
| ปุ่ม Merge เทา | ยังไม่ผ่าน CI หรือยังไม่ Approve | ดู Checks และ Reviews |
| Bot กับ Reviewer ขัดแย้งกัน | AI ต่างกัน | คุณตัดสินด้วยโค้ดและ Spec — บันทึกใน Handoff ส่วน 4 |
| บทเรียนยาวเป็นเรื่องเล่า | ไม่ตัดให้สั้น | ตัดเหลือ 1–2 บรรทัด ตรวจได้ ชี้ PR |

## 🧪 ท้าทายเพิ่ม

- เขียนบทเรียนเป็น **Decision**: เพิ่ม 1 บรรทัดใน `docs/memory/decisions.md` (ผลของการตัดสินใจที่ทีมคุยกันวันนี้ พร้อมเหตุผลสั้น ๆ)
- เปิด **Discussion** เพื่อถามทีมอื่นว่าควรเปลี่ยนกติกาเรื่องใดบ้างก่อนบันทึกลง conventions

## 🧑‍🏫 หมายเหตุสำหรับผู้สอน/TA

- เดินดูการ Review: ใครกด Approve เร็วเกินไปโดยไม่ถามอะไร → ให้อ่านโค้ดอีกรอบและถามหนึ่งข้อ
- แจ้ง Maintainer ล่วงหน้าให้พร้อมรับ PR บทเรียน 5 ใบ (ตรวจ **เนื้อหา** ไม่ใช่แค่กด merge) — เตรียมคำถามตรวจเช่น "ตรวจได้ไหม" "ชี้ PR ไหม" "ซ้ำกับของเดิมไหม"
- ถ้ามีบทเรียน "ผิด" หลุดมา ให้ใช้เป็นกรณีศึกษา memory poisoning (ไม่ประจาน)
- รวบรวม "AI เจอ/พลาด/แจ้งเกินจริง" ที่น่าสนใจ ไว้โชว์ตอน Sprint Review (WS8.3)
